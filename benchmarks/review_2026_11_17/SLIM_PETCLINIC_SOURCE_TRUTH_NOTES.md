The two positive dead-code labels have whole-file evidence: `use function htmlentities` at `Slim/Error/Renderers/PlainTextErrorRenderer.php:17` and `use RuntimeException` at `Slim/Handlers/Strategies/RequestResponseNamedArgs.php:16` are unused lexical aliases. The spelling occurs exactly once in each entire file, at the import declaration. Neither declaration executes imported code. The second file's three interface imports are actually referenced, and the first file's `get_class` and `sprintf` function imports are actual calls; the ledger includes the latter two as used controls. Removing a public class solely because no downstream consumers are in this library would be invalid, and no such label is proposed.

The source search inspected 72 Slim PHP production files, 30 Petclinic Java main files and 20 Java test files for simple unused import candidates. This was a lexical candidate finder followed by full-file manual review, not an analyzer run. It can miss aliases, annotations and other complicated patterns and is not a complete dead-code oracle. No Java unused import emerged. A private PHP constructor initially appearing to have no literal-name caller was rejected: `RouteContext::fromRequest` creates it with `new self` at line44. The ledger retains that as a used control. Petclinic's unused `Locale` formals are required by `Formatter` signatures; their methods have explicit test-source calls and component registration.

Used labels include PHP string callbacks (`isRoute`, `isMiddleware`), a magic invokable strategy, the private constructor, registered renderers and private methods. Java labels include controller routes, bean factories, interface overrides, inherited getters, derived repository methods and private helpers. Framework roots are intentional keep points. Checked-in tests are source evidence of intended calls; they were not executed. Exact definition coverage must be checked later. If a Java method is absent from parsed definitions, that fact is **incomplete**, not a true negative or pass.

Petclinic's three safe security labels concern only open redirect: a fixed `/vets.html` path and two `/owners/` prefixes followed by the inherited `Integer` id. They do not establish authorization, query safety, XSS safety, or safety of the application. These are correlated controls of one security rule, not broad vulnerability coverage. Slim's generic response emitter has native output sinks, but caller-selected bytes, content type and application provenance are not established; those sites remain unknown. The HTML exception-message slot is escaped correctly for its element-text context, but returning a string from `sprintf` is not the direct PHP sink being benchmarked. That construction fact earns no detector TN/pass credit. The XML parser has visible guards, but no deployed runtime contract was verified and no corresponding PHP rule was confirmed; it also earns no credit.

There are **no established unsafe security positives** here and **no Java unused positives**. These labels cannot estimate security recall or Java dead-code recall, cannot certify the full repositories, and cannot support automatic removal. All unlabeled sites remain unknown. The next reviewer should verify source claims and scoring applicability separately, especially framework roots, inherited type evidence, and scope exclusions.
